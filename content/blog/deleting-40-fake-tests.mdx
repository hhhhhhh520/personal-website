# 我删了 40 个能通过的测试：一次测试治理复盘

243 个测试全部绿灯，本地 vitest 从来没红过。直到有一天我打开一个测试文件的 import 区，发现它一行生产代码都没引入。

那个测试测的是谁？测它自己——文件里用函数定义复制了一份被测逻辑，然后断言这份复制品行为正确。生产代码改了，它照样绿。这样的「测试」一共有 40 个，藏在 4 个文件里。这篇复盘整个发现、删除、重建的过程，以及为什么我认为这次「测试数量下降 17%」是项目测试质量最高的一刻。

## 怎么发现假测试的

起因不是测试失败，是一次代码审查时的较真。

当时在给个人网站的 RAG 模块做一轮审查（这个项目踩过的坑记在 issues/ 目录里），第一条 ISSUE 就是「测试与实现脱节」。验证方法简单到离谱：

```bash
# 一个测试文件如果不 import 生产代码路径，它测的是谁？
grep -L "\.\./utils" rag/__tests__/*.test.ts
```

列出来的文件里，有几个长这样：

```ts
// STUB 测试的典型长相
import { describe, it, expect } from 'vitest';

// ❌ 在测试文件里"复制"了一份实现
function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}

describe('cosineSimilarity', () => {
  it('平行向量相似度为 1', () => {
    expect(cosineSimilarity([1, 0], [1, 0])).toBe(1);
  });
  // ……全部通过，永远通过
});
```

这份复制品和 `rag/utils/similarity.ts` 里的真实实现高度相似——因为写测试的时候是从实现里拷出来的。但从此以后两者毫无关系：真实实现改出 bug，测试照绿；复制品自己有 bug，测试照红但和生产毫无关系。

**它是一个绿色的圆圈，不是一张安全网。**

## 它们是怎么混进来的

复盘成因比复盘 bug 更重要，因为假测试的滋生有明确的土壤：**把「测试数量」当进度指标**。

当时的状态：CI 里跑着两百多个测试，数字很漂亮。于是新增模块时顺手写几个「测试」，最省事的路径就是把实现拷进来测一遍——既不用处理模块导出，也不用 mock 依赖，五分钟出一个全绿的测试文件。数量上涨，绿灯常亮，没有任何信号提示不对劲。

还有一类更隐蔽：**测 mock 而不是测实现**。集成测试里 mock 了检索层，然后断言「调用检索时传了正确的参数」。至于真实的检索层返回什么、上下游拼接对不对，没人测。这类测试仪式感十足，防回归能力为零。

回看有两个教训：

1. **「全绿」是弱信号。** 243 个测试全绿和 243 个测试里 40 个是空转，在外部观察上完全一样。指标本身不提供保证。
2. **覆盖率也救不了。** 对复制品做覆盖率统计，覆盖率照样是高的——因为「被测代码」（复制品）确实被执行了。覆盖率衡量的是执行，不是断言有效性。

## 治理四步

发现问题后没有立刻动手，先把治理方案拆成了四步，一次提交做完。

**第一步：删除。** 4 个 STUB 文件整体移除，约 40 个测试。没有犹豫期——复制品测试的维护成本为负（你还以为它们在保护你）。

**第二步：重写，指向真实模块。** 原来的 chat-integration、e2e、index 三组测试改成导入真实实现：

```ts
// 重写后：import 区必须出现生产代码路径
import { buildRAGContext } from '../utils/ragContext';
import { hybridSearch, isIndexReady } from '../utils/ragIndex';

describe('RAG 上下文构建（真实实现）', () => {
  it('空检索结果时返回空上下文', () => {
    expect(buildRAGContext([])).toBe('');
  });
});
```

规则只有一条：**import 区看不到生产代码路径的测试文件，不算测试**。

**第三步：为「测不了」的逻辑恢复可测试性。** 重写时撞上一个结构问题：上下文构建逻辑原本内联在 `app/api/chat/route.ts` 的 handler 里，从测试文件根本 import 不到。解法是可测试性重构——把 `buildRAGContext` 抽成独立模块，route handler 只做调用；顺手删了一段没有调用方的死代码。

这一步是假测试问题的根源之一：**逻辑藏在不可导入的地方，写测试的人只好复制一份**。可测试性差的地方，就是假测试的温床。

**第四步：补上真实覆盖的空洞。** 删掉假测试后暴露了真实空洞——RAG 索引的增量更新逻辑（数据哈希比对、脏检查）此前只有「复制品」在测。用 Python 对着真实的 `build_index.py` 补了 8 个用例，专测哈希计算和增量跳过逻辑。

## 243 → 204：数字降了，信心升了

治理结果：

- TypeScript 测试 204/204 通过，Python 测试 8/8
- 测试总数 243 → 204，降了 17%
- 新增的每一行测试都指向真实生产代码

数字下降反而是这次治理里我最满意的部分。判断一个测试套件的价值，别数测试有多少个，做这个思想实验：**往生产代码里故意注入一个 bug，哪个测试会红？** 治理前，注入到 RAG 工具函数里的 bug 只有部分会被抓到——因为有一半「测试」测的是复制品。治理后，所有红灯都意味着生产代码真的坏了。

现在维护 issues/ 的时候，「测试与实现脱节」这一条的处理经验也沉淀成了规矩：新测试合入前看一眼 import 区，PR 里新增的测试文件如果没有任何生产代码导入，直接打回。

## 检测假测试的三个信号

这套方法可以迁移到任何项目，人工审查盯这三个信号：

| 信号 | 检查方法 | 危险等级 |
|------|----------|----------|
| import 区没有生产代码路径 | `grep -L` 扫测试目录 | 🔴 致命：测的是复制品 |
| 测试文件里有与实现同名的本地函数 | 全局搜索函数定义重复 | 🔴 致命：双份实现必然漂移 |
| 断言全是恒真式 | 看有没有对真实输出值的断言 | 🟡 高危：仪式性测试 |

想自动化的话，第一个信号一条命令就能接进 CI：

```bash
# 测试文件必须 import 生产代码，否则本地检查/CI 失败
for f in rag/__tests__/*.test.ts; do
  grep -q "\.\./utils" "$f" || { echo "$f 未导入生产代码"; exit 1; }
done
```

## 与「多测试之路」的对照

我另一篇写 Mini Claude Code 的测试之路，那是「数量」的故事——1700 多个测试怎么随功能迭代自然长出来。这一篇是「质量」的故事：数量增长到某个阶段，如果不治理有效性，套件会悄悄烂掉。两个项目现在遵循同一条底线：**测试的价值不在于它存在，而在于它失败的时候你真的出事了**。

## 总结

| 阶段 | 动作 | 结果 |
|------|------|------|
| 发现 | 审查测试文件的 import 区 | 找到 4 个 STUB 文件 |
| 删除 | 移除约 40 个复制品测试 | 243 → 204 |
| 重写 | 指向真实模块 + 可测试性重构 | buildRAGContext 抽为独立模块 |
| 补洞 | Python 测真实增量逻辑 | 8 个用例覆盖哈希/脏检查 |
| 防回归 | 「import 生产代码」规则进审查清单 | 假测试不再有温床 |

一句话版本：**先怀疑「全绿」，再相信「全绿」**。你的测试套件里，可能正躺着几个只会在自己世界里通过的家伙。
